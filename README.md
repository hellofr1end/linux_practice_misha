# Практикум: Пользователи, группы и права доступа в Linux

## Подготовка к работе
Все задания выполняются в терминале Linux (или WSL). Для создания пользователей, групп и смены владельцев потребуется `sudo`.

---

## Задание 1. Секретная база (Разделение доступа по группам)

### Контекст
На сервере работают трое: вы (администратор), ваш напарник `friend` и посторонний пользователь `hacker`. Необходимо организовать закрытую рабочую директорию для совместной работы с напарником так, чтобы `hacker` не мог ни просмотреть её содержимое, ни войти в неё.

### Требования
1. Создайте двух новых пользователей: `friend` и `hacker` (через `sudo adduser`).
2. Создайте новую группу `bro`.
3. Добавьте свой основной аккаунт и пользователя `friend` в группу `bro`. Пользователь `hacker` не должен состоять в этой группе.
4. Создайте директорию `/tmp/secret_base`.
5. Внутри неё создайте файл `plan.txt` с любым текстовым содержимым.
6. Назначьте группу `bro` группой-владельцем директории `/tmp/secret_base` и файла `plan.txt`.
7. Выставьте права на директорию `/tmp/secret_base` так, чтобы владелец и участники группы `bro` имели полный доступ (`rwx`), а все остальные пользователи не имели никаких прав (`---`).
8. Выставьте права на файл `plan.txt` так, чтобы владелец и участники группы `bro` могли его читать и изменять (`rw-`), а остальные не имели доступа.

### Критерии проверки
- При переключении на `hacker` (`su - hacker`) попытка выполнить `cd /tmp/secret_base` или `ls /tmp/secret_base` завершается ошибкой `Permission denied`.
- При переключении на `friend` (`su - friend`) пользователь успешно заходит в директорию, читает файл `plan.txt` и может дописать в него новую строку.

## Задание 2. Сломанный деплой (Права на исполнение скриптов)

### Контекст
Разработчики выложили на сервер скрипт автоматического резервного копирования, но при попытке его запустить система блокирует выполнение. Необходимо настроить права так, чтобы скрипт мог запускать только его владелец, при этом остальные пользователи могли читать его исходный код для аудита, но не могли изменять.

### Требования
1. Создайте директорию `/tmp/deploy`.
2. Создайте внутри файл `backup.sh` со следующим содержимым:

```bash
#!/bin/bash
echo "Backup started at $(date)"
```

3. Попробуйте запустить скрипт из директории `/tmp/deploy` командой `./backup.sh` и зафиксируйте ошибку доступа.
4. Назначьте на файл `backup.sh` права в восьмеричном (числовом) формате, соответствующие следующим правилам:
   - Владелец: чтение, запись, выполнение.
   - Группа: чтение и выполнение.
   - Остальные: только чтение.
5. Убедитесь, что скрипт успешно запускается от имени вашего основного пользователя.

### Критерии проверки
- Вывод команды `ls -l /tmp/deploy/backup.sh` показывает маску прав `-rwxr-xr--`.
- Команда `./backup.sh` выводит текущую дату и сообщение без ошибок.
- Пользователь `hacker` может прочитать содержимое файла через `cat`, но при попытке выполнить `./backup.sh` получает `Permission denied`.

## Задание 3. Утечка паролей (Аудит и закрытие уязвимости)

### Контекст
Предыдущий администратор по неосторожности оставил конфигурационный файл базы данных с открытыми правами для всех пользователей системы. Любой пользователь на сервере может прочитать пароли и перезаписать настройки. Необходимо провести аудит и закрыть уязвимость.

### Требования
1. Создайте файл `/tmp/db_credentials.env` и запишите в него строку `DB_PASSWORD=SuperSecretPassword123`.
2. Выдайте файлу максимально открытые права `777`. Проверьте результат через `ls -l`.
3. Измените права доступа на файл `db_credentials.env` таким образом, чтобы:
   - Только владелец мог читать и редактировать файл.
   - Никто другой (ни группа, ни остальные пользователи) не мог ни читать, ни изменять, ни запускать этот файл.
   - У самого владельца не было лишнего права на выполнение (`x`), так как это текстовый конфиг, а не программа.

### Критерии проверки
- Вывод команды `ls -l /tmp/db_credentials.env` отображает права `-rw-------` (числовой эквивалент `600`).
- Попытка прочитать файл от имени `friend` или `hacker` (`cat /tmp/db_credentials.env`) завершается ошибкой `Permission denied`.

## Задание 4. Ловушка с удалением (Разница прав файла и директории)

### Контекст
На практике новички часто путают права на файл и права на директорию, в которой этот файл лежит. Ваша задача — на практике доказать, что удаление файла регулируется правами родительской директории, а не правами самого файла.

### Требования
1. Используйте директорию `/tmp/secret_base` из Задания 1 (где у группы `bro` есть права `rwx`, а значит есть право на запись `w`).
2. От имени вашего основного пользователя создайте внутри `/tmp/secret_base` файл `untouchable.txt` с текстом `Do not delete me`.
3. Выставьте на файл `untouchable.txt` строгие права `600` (`-rw-------`), чтобы даже участники группы `bro` не могли его прочитать или отредактировать.
4. Переключитесь на пользователя `friend` (`su - friend`), который состоит в группе `bro`.
5. От имени `friend` попробуйте прочитать файл: `cat /tmp/secret_base/untouchable.txt`. Убедитесь, что система запрещает это делать.
6. От имени `friend` попробуйте удалить этот же файл: `rm -f /tmp/secret_base/untouchable.txt`.

### Критерии проверки
- Пользователь `friend` не смог открыть файл `untouchable.txt`, но смог беспрепятственно его удалить.
- Объясните устно или в отчете, почему так произошло, опираясь на значение бита `w` для директорий в Linux.

## Очистка системы после выполнения практикума
После проверки всех заданий удалите тестовые файлы, пользователей и группу, чтобы не оставлять мусор в системе:

```bash
sudo rm -rf /tmp/secret_base /tmp/deploy /tmp/db_credentials.env
sudo deluser --remove-home friend
sudo deluser --remove-home hacker
sudo groupdel bro
```
